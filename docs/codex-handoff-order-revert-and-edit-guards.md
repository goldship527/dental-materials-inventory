## 0. 背景と目的

自動発注候補（次工程③）は「未納数量」を差し引いて候補数を計算する。未納数量が誤ると候補が過不足するため、先に次の欠陥を直す。

| # | 現状（事実） | 影響 |
|---|---|---|
| A | 部分納品の取り消し（`revertOrderReceiptForContext`）は、不足分として自動作成した繰越発注に触れない（spec §87.6 の既知制約） | 3個中2個受領→取り消しで、元発注3個＋繰越1個＝納品待ち4個になる（実際は3個） |
| B | 繰越発注と元発注の関連は `memo` の文言だけで保持している（`applyOrderReceiptLine` の `元発注 ${id} の不足分 ${n} を繰越`）。状態変更は `memo` を上書きする | 関連を機械的にたどれない |
| C | 発注数量の変更（`updateOrderRequestQuantityWithStateAction`）は状態を確認せず、ロックもない。画面の「数量変更」も全状態で表示される | 納品済みの行の数量も変えられる。同時操作で後勝ちになる |
| D | 状態変更（`updateOrderRequestStatusForContext`）は対象をトランザクション外で読み、ロック・状態の再確認なしで更新する | 納品確定と同時に「納品待ち→見送り／発注予定」へ変更すると、受領済みなのに見送り等の不整合が起き得る。`納品待ち→発注予定` で同じ商品の発注予定が2行になり得る |

## 1. 仕様案（`docs/spec.md` §94 として反映する案文）

### 94. 部分納品取り消しの繰越整理と、発注候補の変更制約

#### 94.1 繰越発注の関連

- `OrderRequest` に、繰越元を示す任意の自己参照 `backorderOfId` を追加する。部分納品で不足分の発注を作る時に、元発注のIDを保存する。
- `memo` の繰越文言は表示用として従来どおり残すが、関連の判定には使わない。
- 既存データの補完: 公開DBで繰越発注（`memo` が繰越文言を含み、`status = ORDERED`）の件数を読み取りで確認し、0件なら補完しない。1件以上なら、別途承認を得て、プレビュー→バックアップ→補完の手順で行う。

#### 94.2 部分納品の取り消し

- 元発注の納品確認を取り消す時、同じトランザクション内で `backorderOfId = 元発注ID` の繰越発注を確認する。
  - 繰越発注が**未受領**（`receivedAt = null`）なら、状態にかかわらず削除する。元発注は従来どおり未受領の `ORDERED`（発注数は元の数量）に戻るため、納品待ちの合計は正しい数に戻る。
  - 繰越発注が**受領済み**なら、取り消しを拒否する。案内:「不足分の納品が確認済みのため取り消せません。先に不足分の納品確認を取り消してください。」（新しい受領から順に取り消す）
- 部分受領だった元発注（`receivedQuantity < requestedQuantity`）で、関連する繰越発注が見つからない場合は、取り消しを拒否する（補完前の旧データの安全策）。案内:「不足分の発注を特定できないため取り消せません。管理者に連絡してください。」
- 全数受領の取り消しは従来どおり。
- ロック順: 元発注の `order-receipt:<元ID>` → 繰越発注の `order-receipt:<繰越ID>` → `stock-item:<clinic>:<product>`。

#### 94.3 発注数量の変更

- 変更できるのは、`発注予定`（`DRAFT` / `CONFIRMED`）と、`納品待ち`（`ORDERED` かつ未受領）だけとする。`納品済み` と `見送り` は変更不可。
- 画面の「数量変更」も上記の状態でだけ表示する。
- サーバーは `order-receipt:<ID>` のロックを取り、`status`・`receivedAt` を条件にした条件付き更新を行う。更新件数0なら「状態が変わりました。一覧を更新してください。」を返す。

#### 94.4 状態変更

- 対象の読み取りから更新までを1つのトランザクションで行い、`order-receipt:<ID>` のロック後に状態と `receivedAt` を再確認する（既存の「納品済みは戻せない」規則をロック下で判定する）。
- `納品待ち→発注予定`（発注記録の取り消し）と、`見送り→発注予定` へ変更する時は、`order-request:<clinic>:<product>` のロックを先に取り、同じ商品の別の発注予定があれば拒否する。案内:「同じ商品の発注予定がすでにあります。」
- `納品待ち→見送り` は「未納の打ち切り（入荷しない分を待たない）」として扱う。見送りにした行は納品待ちの合計から外れる。
- 状態変更で `memo` を更新しても、`backorderOfId` は変更しない。
- ロック順は常に `order-request:...` → `order-receipt:...` とする。

#### 94.5 エラー表示

- 発注・納品の操作で、想定した業務エラー以外の例外（Prisma の内部エラー等）は、内部の文言を画面へ出さず「結果を確認できませんでした。入出庫履歴と最新の一覧を確認してから操作してください。」と表示する。（§2 D4 で採用した場合のみ）

#### 94.6 今回作らないもの

- 自動発注候補（§95 として別途確定）
- 分納の専用画面、欠品理由の管理、納品書照合
- 発注先変更（`updateOrderRequestSupplierForContext`）のロック強化（対象が発注予定のみで影響が小さいため後回し）

## 2. ユーザー決定事項（実装前に確定する）

| # | 論点 | 推奨（D1〜D4は2026-10-07に採用決定） | 理由 |
|---|---|---|---|
| D1 | `納品待ち` の数量変更を許すか | 許す | 先方都合で入荷数が減った場合などを反映する唯一の手段。納品済みは不可 |
| D2 | `納品待ち→見送り` を「未納の打ち切り」として正式化するか | する | 届かない繰越が未納として残り続けると、自動候補が出なくなる。新しい状態は増やさない |
| D3 | `納品待ち→発注予定`（発注記録の取り消し）を残すか | 残す（同じ商品の発注予定が既にあれば拒否） | 誤って発注記録した場合の戻し手段 |
| D4 | エラー文言の日本語化（§94.5）を今回含めるか | 含める | 同じファイルの小変更。今回の本番エラーで英語の内部文言が出た |
| D5 | 公開DBへのスキーマ反映（列追加）を承認するか | 承認する場合は §4 の手順で | 追加のみ・任意列で既存データは変わらないが、本番DBの変更のためT4 |

## 4. 公開DBへのスキーマ反映（ユーザー承認後・Codexは承認なしに実行しない）

1. 公開DBで、繰越発注の件数と、部分受領済みの元発注の件数を**読み取りだけ**で数える（値・商品名は記録しない。件数のみ）。
2. 件数と、追加する列・索引の内容をユーザーに提示し、承認を得る。
3. `scripts/push-supabase-schema.ps1` 実行前に、`prisma db push` が列追加以外の変更（削除・型変更・データ損失警告）を含まないことを確認する。警告が出たら中止する。
4. 反映後、`The database is already in sync` を確認してから、アプリを公開する（列が無い状態で新コードを公開しない）。
5. 1 の件数が1件以上なら、補完は別手順で承認を取る。
