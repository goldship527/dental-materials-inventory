## 0. 目的

- 基準在庫を下回ったら、不足分を「確認待ち」の発注候補として商品ごとに1行で示す。外部へは送らない。
- スタッフが確認して数量を決めた候補（発注予定）は、自動で変更しない。
- 在庫訂正などで不足が解消したら、確認待ちの候補は自動で減る・消える。過剰な候補を残さない。

## 1. 仕様案（`docs/spec.md` §95 として反映する案文）

### 95. 自動発注候補（確認待ち）

#### 95.1 状態

- `OrderRequestStatus` に `SUGGESTED` を追加し、画面表示は「確認待ち」とする。既存の `DRAFT`（画面上は発注予定）の意味は変えない。
- 確認待ちは**自動管理**の候補である。数量はシステムが再計算し、スタッフはまだ判断していない。
- 確認待ちは、発注書下書き、発注記録の一括操作、発注先ごとの発注書印刷の対象に**含めない**（`printableOrderRequestStatuses` は `DRAFT`・`CONFIRMED` のまま）。
- 1つのクリニックの1商品につき、確認待ちは最大1行とする。

#### 95.2 目標数の計算

```
目標数 = 基準数 − 現在庫 − 納品待ち数量 − 発注予定数量
```

- 基準数: `StockItem.minStock ?? Product.defaultMinStock`（既存の不足判定と同じ）
- 現在庫: `StockItem.quantity`
- 納品待ち数量: その商品の `ORDERED` かつ `receivedAt = null` の `requestedQuantity` 合計（§94で繰越を正しく数える）
- 発注予定数量: その商品の `DRAFT`・`CONFIRMED` の `requestedQuantity` 合計
- 数量は**在庫単位**で扱う（現行の納品は受領数をそのまま在庫へ加算するため）。画面では「不足 N（単位）」と単位を付けて表示し、包装への読み替えは発注書作成時に人が行う。

#### 95.3 再計算の規則（自動管理）

再計算は、対象商品の現在状態だけから目標数を求める（差分の足し込みはしない）。同じ再計算を何度実行しても結果は同じになる。

| 状況 | 動作 |
|---|---|
| 対象外の商品（§95.4） | 確認待ちがあれば削除する |
| 自動停止中（§95.6） | 何もしない（確認待ちは作らない。既存の確認待ちは見送り時点で無くなっている） |
| 目標数 > 0、確認待ちなし | 目標数で確認待ちを作成する（発注先は主発注先） |
| 目標数 > 0、確認待ちあり | 数量を目標数へ更新する（増減どちらも） |
| 目標数 ≤ 0、確認待ちあり | 確認待ちを削除し、監査ログ（`AuditLog`、action `order_suggestion.removed`、件数・数量のみ）を残す |
| 目標数 ≤ 0、確認待ちなし | 何もしない |

- 発注予定・納品待ち・納品済み・見送りの行は、再計算で**一切変更しない**。

#### 95.4 対象外

次のいずれかに当たる商品は確認待ちを作らない（あれば削除）。

- 基準数が0以下
- 商品が無効、または在庫行が利用中でない（`isUsed = false`）
- 使用中管理の商品（`stockUsageMode` が `NONE` 以外）
- 単位を特定できない商品（カード出庫と同じ `cardStockUnit` が `null`）

#### 95.5 再計算を呼ぶ処理

次の処理のトランザクション内で、在庫・発注の更新を終えた後に、対象商品の再計算を呼ぶ。在庫や発注が変わってもその場で呼ばれなかった場合でも、次に呼ばれた時点で正しい値に戻る（状態からの計算のため）。

1. カード出庫（`issueFromCard`）
2. 在庫訂正・クイック増減・バーコード出入庫・一括出庫（`stock.ts`、`barcode-stock.ts`、`barcode-batch.ts`）
3. 棚卸の確定（簡易棚卸、棚卸セッション）
4. 入出庫履歴の取り消し（`revertStockMovementForContext`）
5. 納品確定・一括納品・納品確認取り消し
6. 発注候補の手動追加・状態変更・数量変更・発注記録（一括を含む）
7. 最低在庫の変更（在庫行の個別最低在庫、商品の基準数、購入履歴の一括整備）

#### 95.6 スタッフの操作

| 操作 | 結果 |
|---|---|
| 確認待ちを「確認」 | 発注予定（`CONFIRMED`）へ移る。以後は自動で変わらない |
| 確認待ちの数量を変更 | 変更した数量で発注予定へ移る（数量変更＝人の判断） |
| 確認待ちの発注先を変更 | 確認待ちのまま（数量の自動管理は続く） |
| 確認待ちを「見送り」 | 見送り（`SKIPPED`）にし、その商品の**自動停止**を開始する |
| 発注予定を「見送り」 | 同上（人が「今回は発注しない」と判断したため） |
| 不足一覧の「候補へ追加」 | 確認待ちがあれば、それを発注予定へ移す（行を増やさない）。なければ従来どおり作成 |
| 確認待ちから直接「発注を記録」 | 不可。先に確認して発注予定にする |

- 自動停止: `StockItem.autoOrderSuppressedAt` に日時を記録する。停止中は確認待ちを作らない。
- 自動停止の解除: (a) 再計算で目標数が0以下になった時（不足が解消した時）、(b) 不足一覧の「候補へ追加」など、その商品の発注予定を人が作った時。
- 不足一覧と発注画面には、停止中の商品に「見送り中（自動候補停止）」を表示する。

#### 95.7 排他制御（ロック順）

再計算は `order-request:<clinic>:<product>` のロックの下で行う。デッドロックを避けるため、全経路で次の順序を守る。

1. `order-request:<clinic>:<product>`（商品単位。**その商品の在庫行・発注行を更新する前に最初に取る**）
2. `order-receipt:<orderRequestId>`（発注行単位）
3. 在庫行の更新（行ロック）、`stock-item:<clinic>:<product>`

- 商品IDを知るための最初の読み取りはロックなしで行い、ロック取得後に対象を読み直して検証する（§94.4 と同じ方式）。
- 複数商品を扱う処理（一括出庫・一括納品・発注記録の一括）は、商品IDの昇順にロックを取る。
- 現行の納品確定は `order-receipt` だけを取って在庫行を更新しており、カード出庫は在庫行を更新しても商品単位のロックを取らない。本節に合わせて、両方とも商品単位のロックを最初に取るよう変更する。

#### 95.8 画面

- 発注画面: 状態フィルタと件数に「確認待ち」を追加する。確認待ちの行には「確認して発注予定へ」「数量を変えて発注予定へ」「見送り」を置き、「不足 N（単位）」と、計算の内訳（基準・現在庫・納品待ち・発注予定）を1行で表示する。
- ホーム: 「今日の注意」に「確認待ち N件」を追加し、発注画面の確認待ちへ移動できるようにする。
- 発注書下書き・印刷・発注記録の一括操作には確認待ちを出さない。
- 本部ダッシュボード（読み取り専用）は件数に確認待ちを含めて表示する。

#### 95.9 既存仕様の変更

- §88.1「基準数との一致で発注を自動作成する変更はしない」→ 一致では作らない点は維持し、「基準未満では§95に従い確認待ちを自動作成する」を追記する。
- §76.1・§76.2 に確認待ち（`SUGGESTED`）を追加する。§76.4「DBスキーマとEnumは変更しない」に§95の例外を明記する。
- README「まだ作らないもの」に、外部への自動発注送信は引き続き作らないと明記する。

#### 95.10 今回作らないもの

- 外部への自動発注送信、メール通知（朝のダイジェストへの追加を含む）
- 包装単位への自動換算（§88.4 の確認後）

## 4. 公開DBへの反映（ユーザー承認後）

§94 と同じ手順で行う。

1. 利用者が差分SQLを読み取りで表示し、`ALTER TYPE "OrderRequestStatus" ADD VALUE 'SUGGESTED'` と `ALTER TABLE "StockItem" ADD COLUMN "autoOrderSuppressedAt"` だけであることを確認する。
2. 利用者が `scripts/push-supabase-schema.ps1` を実行する。
3. 同期を確認してからPRをマージし、本番公開する。公開後、確認待ちが出るのは次の在庫変動からで、既存在庫に対する一括作成は行わない。
