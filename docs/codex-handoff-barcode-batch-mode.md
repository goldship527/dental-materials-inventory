## 1. 目的

現場で納品・出庫が大量に発生する場面で、1件ずつ画面操作して確定する現行フロー（`/barcode/stock`）は遅く、件数が多いと負担が大きい。
そこで、**バーコードを連続で読み取り、画面上のリストにためてから最後に一括確定する**高速処理モードを追加する。

重視する点:

- 連続出庫モード／連続納品モードの2つを用意する。
- 読み取りごとに即DB更新しない。いったん画面のリストにためる。
- 最後に内容を確認して一括確定する。
- 誤スキャン時にリスト上で行削除・数量修正ができる。
- 作業スタッフの記録は現状仕様どおり、共通ヘッダーの作業スタッフ選択（`work-staff-selector` / `useWorkStaffSelection`）を使う。
- 安全性とスピードのバランスを取る（読み取りは速く、DB変更は確定時にまとめて安全に）。

### 最優先方針（2026-06-09 オーナー判断・優先度を再設定）

**本丸は「納品」。出庫は軽い。** 大量に届く納品（紙の納品書中心、一部はディーラーの電子データ、ネットショップ購入も混在）を速く捌くことが最重要。出庫は件数が少ないので**バーコードスキャンだけで十分**とする。

> 注記: 当初は「出庫ステーション（スキャン＋タップカード＋名前検索）」を中心に据えていたが、実際の業務量を確認した結果、**出庫は軽く・納品が本丸**と判明したため方針を再設定した。**出庫ステーション構想は取り下げ**、出庫はシンプルに保つ。本書の以降の記述はこの再設定が優先する。

優先順位:

1. **納品（最優先・大量）**: 「**受領確認リスト → 一括受領確定**」を中心に据える。入力経路を段階的に増やす（後述）。
2. **出庫（軽量）**: バーコードの連続スキャン出庫のみ。無バーコードの稀な出庫は既存クイック出庫／手動でカバー。**出庫ステーション（タップ／検索）は作らない。**

### 納品の中心設計：受領確認リスト → 一括確定（最優先）

納品は「**読み込む → 確認 → どんどん足す → 一括確定**」の1本の流れにする。**入力経路を1つの受領確認リストに集約**し、人が確認してから一括で受領確定（`OrderRequest` 受領＋在庫＋ロット反映）する。大量に来るので、1点ずつ確定ではなく**リストにためてまとめて確定**が要。

入力経路（段階導入。オーナー判断＝**スキャン納品＋確認リストを最初に**）:

1. **バーコードスキャン納品（最初に作る・MVP）**: 届いた品のバーコードを連続スキャン → 受領確認リストに積む → 納品待ち `OrderRequest` と照合 → 内容確認 → 一括受領確定。
2. **電子データ取込（後で同じリストに追加）**: ディーラーのCSV/Excel。既存「購入履歴インポート」のプレビュー&確認UXを流用。OCR不要で確実。
3. **紙の納品書OCR（さらに後で同じリストに追加）**: ネットショップ等の紙伝票を撮影 → OCR → 同じ受領確認リストへ。仕入先レイアウト差・誤読が課題なので**必ず人手確認**（現場制約F）。

**重要**: 受領確認リストは**無バーコード品もそのまま扱える**（明細行を名前／コードで照合）。納品側の無バーコード不安はこれで解消する。

### 出庫はバーコードのみ（シンプル）

- 出庫＝**バーコードの連続スキャン出庫のみ**。タップカード／名前検索の「出庫ステーション」は**作らない**。
- 無バーコードの稀な出庫は、既存のクイック出庫（`/quick`）または在庫一覧の手動編集でカバー。`/quick` はそのまま残す。

### 導線とトップ構成

- クリニック共通ログイン=STAFF（現場）、個人ログイン=ADMIN（事務）という既存方針を活かす。
- STAFFはログイン後、最短で**納品／出庫の作業画面**へ到達できるようにする（着地画面の具体は設計裁量）。不足・発注などのダッシュボードはADMIN向けに残す。
- 着地画面の変更は**非破壊**で進める。まずホーム最上部に「納品」「出庫（バーコード）」への大きな導線を置き、運用が固まってからSTAFF直接着地に寄せる、という二段構えを推奨。
- **クイック出庫（`/quick`）は残す**（無バーコード出庫の受け皿として有用）。

#### キオスク運用（端末据え置き。2026-06-09 オーナー判断）

- **共有端末を「常時ログインのまま作業画面に据え置く」キオスク運用にする。** これで「ログイン」は朝1回の費用に償却され、作業ごとには発生しない。実質コストは「スキャン群＋確定」だけになる。
- 着地: STAFFのキオスク端末は、起動／復帰時に作業画面へ戻る（操作後・確定後も作業画面に留まる）。
- アカウンタビリティ: 常時ログインは**クリニック共通STAFFアカウント**で行い、**誰が操作したかは“ログイン”ではなくバッチごとのスタッフバーコード**で記録する（現場制約A）。共有端末の名義はスタッフバーコードで担保するので、共通ログイン据え置きでも記録は個人単位で残る。
- 運用上の配慮（任意）: 無操作が続いたら作業画面のトップへ自動で戻す、ADMIN機能は別ログインに分離したまま（キオスクからは触れない）等。

#### 操作モデルの再検証結果（2026-06-09）

- 「本当に最速か」を再検証した結果、**操作モデルより業務の優先度（納品が本丸）を正すことが先**と判明した。操作自体は安全網を優先し「画面で一括確定（ためて確認してから確定）」を維持する。
- 比較した代替案: ①スキャナのみ完結（確定/取消をコマンドバーコード化・画面非接触）②即時確定＋ワンタップ取消（単品最速だが「ためて確認」の安全網を手放す）。いずれも採用せず、一括確定を維持。
- 速度面は操作モデルよりも**ログインの償却（キオスク化）**と**納品の一括化**で取りに行く、という整理。

### 現場制約への対応（2026-06-09 オーナー確認）

#### A. 出庫は複数スタッフが「共有端末を交代で」行う

- **共有端末前提**。1台を複数スタッフが交代で使う。
- **スタッフ識別はスタッフバーコード読み取りを主手段にする（推奨。2026-06-09 オーナー提案）。** あらかじめ印刷済みのスタッフバーコード（`StaffOperator.barcode`、`STAFF-0001` 形式。印刷ページ `/admin/staff-operators/labels` で発行済み）を読み取って作業スタッフを確定し、続けて商品バーコードを読む流れ。共有端末＋ハンディスキャナに最適で、ドロップダウン選択のタップが消える。
  - 解決は既存 `findActiveStaffOperatorForClinic({ organizationId, clinicId, barcode })` を流用。`normalizeStaffOperatorBarcode` で正規化。
  - スキャン入力欄は、読み取り値が**スタッフバーコードか商品バーコードかを自動判定**する（`STAFF-####` 形式 or `StaffOperator` に一致 → スタッフ設定、それ以外 → 商品として処理）。
  - **ドロップダウン選択（`WorkStaffSelector`）は代替手段として残す**（バーコードを忘れた・読めない場合）。
- 作業スタッフ名は画面上部に**常時・大きく**表示する。
- 当日記憶（`useWorkStaffSelection` の localStorage）は利便のため残すが、**共有端末では名義事故（Bさんの出庫がAさん名義になる）を防ぐため、各一括確定でスタッフを明示確認させる**。確定ダイアログにスタッフ名を出し、違えばその場でワンタップ切替（またはスタッフバーコード再読み取り）。
- スタッフ運用の単位: **1バッチ＝1スタッフ**を既定とする。リストが空でない状態で別のスタッフバーコードを読んだら「スタッフを切り替えますか（現在のリストはどうするか）」を確認する。※ `StockMovement.performedByStaffId` は行ごとに持てるため、将来「行ごとに直前に読んだスタッフを記録（交代しながらの連続作業）」へ拡張する余地はあるが、MVPは1バッチ1スタッフで割り切る。
- バッチ確定後、次バッチ開始時に「このスタッフで続けるか／切替」を促す。スタッフ切替はヘッダーからワンタップ。
- 複数人が同時・連続に同じ在庫を操作してもデータは安全（1トランザクション＋在庫不足ガード＋`pg_advisory_xact_lock`）。論点は記録名義だけ。各 `StockMovement` / `OrderRequest` の `performedByStaffId` / `receivedByStaffId` は確定時点の選択スタッフで記録する。

#### B. バーコードなし／個別出庫時にバーコードが無い商品がある

「バーコードが無い」には種類があり、それぞれ扱いを分ける。**出庫時の商品特定は、次のフォールバック順（上から速い順）で行う**。

1. **個（バラ）自体にバーコードがある** → そのまま読む。
2. **箱・袋（包装）にはバーコードがあるが、個別出庫する1個には無い**（今回の主ケース）
   → **包装バーコードを読んで商品を特定し、数量は 1 にして出庫する。** 在庫は個で数える前提（現場制約 C）なので、包装バーコードは「商品の特定」に使い、数量を 1 に変えるだけでよい。**個別の専用バーコードは不要**。
   → 注意: 案2（入数の自動換算）を入れる際は、包装バーコードに既定数量を持たせると個別出庫で誤って包装数（例 3）が入りやすい。よって「**既定数量は納品時のみ自動適用、出庫時は既定 1**」のルールを守る（現場制約 C 再掲）。
3. **どこにもバーコードが無い商品**
   → 出庫の場合: 既存の**クイック出庫（`/quick`）**または**在庫一覧の手動編集**でカバー（出庫は軽量のため、出庫リストにはタップ／検索入力を作らない）。
   → 納品の場合: **受領確認リストの明細行**として名前／コードで照合できる（納品はリスト方式なのでバーコード不要。納品側の無バーコード不安はこれで解消）。
4. **内部バーコード／棚ラベルを発行して貼る（将来採用方針。2026-06-09 オーナー関心あり）**
   → 無バーコード商品や棚・ビンに、クリニックが印刷した内部バーコードを貼れば、以後はスキャンで特定でき、**最終的に全商品をスキャンで統一**できる。棚ラベル運用は現場で効く。
   → 既存土台: `Product.internalCode`、`ProductBarcode`（`barcodeType` を `INTERNAL` 等にして登録）、Code128/EAN13 描画コンポーネント、ラベル印刷ページ（`/admin/staff-operators/labels` と `/imports/medical-devices/barcode-labels`）が既にある。
   → 重要な前提: 現状 `searchProductsByBarcode` は `janCode` と `ProductBarcode.barcode` を検索対象にするが **`internalCode` は検索しない**。内部コードをスキャン可能にするには、`ProductBarcode` に登録する必要がある。
   → 必要になる主な作業（別ハンドオフで設計）:
     - 商品ごとに一意な内部バーコードを採番（`internalCode` 流用 or 新規採番）し、`ProductBarcode`（`barcodeType="INTERNAL"`）として登録する仕組み。
     - 内部バーコードの**一括発行・印刷UI**（スタッフラベル印刷 `/admin/staff-operators/labels` のCode128印刷が雛形になる。商品版を新設）。
     - 棚・ビン単位で貼るか、商品単位で貼るかの運用設計（棚ラベル＝ロケーション、商品ラベル＝商品特定）。
     - 既存JAN/包装バーコードと内部バーコードが二重に当たらないようにする整合（`@@unique([organizationId, barcode])` があるので衝突は弾けるが、採番規則を決める）。
   → **タイミング**: 実データで「無バーコード商品が何割あるか」（15-2）を見て規模を確認してから着手。MVP（フォールバック 1〜3）を先行で立ち上げ、ラベル運用は次フェーズで足す。

この設計なら、**個別出庫でバーコードが無くても困らない**: 包装バーコードがあれば「読んで数量1」、無ければ既存クイック出庫／手動。納品側は無バーコードでも受領確認リストの明細行で扱える。

#### C. 入数（1袋3個入りで1個だけ出庫、その1個はバーコードなし）

- **在庫は最小単位（個）で数える**ことを前提にする（消費が個単位のため）。`StockItem.quantity` は個数で運用する。
- 納品は袋単位で入ることがある（例: 1袋＝3個入り）。受領数は**個に換算した数**を入れる（1袋なら受領数 3）。
- 1個だけの出庫で、その1個にバーコードが無い場合は、包装バーコードがあれば「読んで数量1」、無ければ**既存クイック出庫（`/quick`）／在庫一覧の手動編集**で数量1出庫（B の仕組み）。
- **入数の扱いは「段階導入」（オーナー判断）**:
  - **MVP（案1・スキーマ変更なし）**: バーコード／タップ／検索は「商品の特定」に使い、**数量は常に編集可**（出庫の既定は 1、納品は受領数を手入力）。袋→個の自動換算はしない。1袋3個納品は受領数 3 を手入力、1個出庫は数量 1。今ある項目だけで表現できる。
  - **次フェーズ（案2・スキーマ変更あり）**: `ProductBarcode` に「**既定入出庫数量**」（例: 袋バーコード=3、バラ=1）を追加し、袋スキャンで自動 +3。spec.md の未実装項目「バーコードごとの既定入出庫数量／包装単位の自動換算」に対応。**別ハンドオフで設計**する。
  - 案2の注意（落とし穴）: 袋バーコードに既定数量 3 を持たせると、「袋を開けて1個だけ使う」出庫で誤って 3 出庫しやすい。案2を作る際は「**既定数量は納品時のみ自動適用、出庫時は既定 1**」等のモード別ルールを別途設計する。

#### D. クリニック呼称（院内呼称・グルーピング）

- 院内では、正式な商品名ではなく**現場の言葉（呼称）**で材料を扱う。例: 製品A・製品B（別SKU・別メーカー）を、院内ではどちらも「グローブ」と呼ぶ。
- **採用方針＝段階2「呼称でまとめて探せる（在庫は製品別）」（2026-06-09 オーナー判断）。**
  - 検索「グローブ」で製品A・Bの**両方**を表示する（呼称でグルーピング）。
  - ただし**在庫・発注・期限/ロットはSKU（製品）単位で正確に持つ**。プール（合算）はしない。
  - 出庫時は、実際に使った製品（AかB）をタップして、そのSKUの在庫を −1。
- 呼称は**クリニック単位**の情報（院ごとに呼び方が違う場合がある）なので、`Product`（組織共通）ではなく**クリニック×製品の行**に持たせる必要がある → **小さなスキーマ追加**になる（例: `StockItem` に院内呼称カラム、または `ClinicProductAlias` / 呼称グループのテーブル）。
- 既存の `FavoriteProductCard.categoryTab`（クリニック単位のカード分類）が近い土台。タップカードのまとめ表示はこれを流用できるが、「呼称」そのものは新規項目。
- **タイミングは入数（案2）と同様に「実データを見てから」**。同じ呼称→別SKUのケースが実際どれだけあるかで、呼称を「製品ごとの別名」だけで足りるか「呼称グループ（多対一）」が要るかが決まる。MVP（案1）は正式名＋名前検索で立ち上げ、呼称グルーピングは次フェーズ・別ハンドオフで設計する。
- 効き方: 納品の受領確認リストや商品検索の**ヒット文言**として呼称を使う（呼称「グローブ」で製品A・Bを探せる）。1呼称が複数SKUに当たるときは候補を展開して実SKUを選ばせる（行はSKU単位）。出庫はバーコードのみなので呼称の主な効き先は納品・検索側。

#### E. 読み取り不良・連続誤読への対策

連続読み取り運用では、1件ずつ確認しないぶん誤読が混ざりやすい。本設計は**「ためて一括確定」モデルそのものが最大の安全網**である点を前提に、入力段で多層の防御を入れる。

**E-0. 大前提（安全網）**
- 各読み取りは即DB反映せず、**商品名つきの編集可能な行**としてリストに積むだけ。確定までDBは変わらない。誤読は一覧で見えて、行削除・数量修正で直せる。さらに確定時にサーバーが全件再検証する（現場制約・セクション7）。

**E-1. 読み取り時の検証（行に積む前にフィルタ）**
- `normalizeBarcodeText` で正規化（全角→半角・ハイフン等）。
- 長さ・文字種チェック（極端に長い／想定外文字は弾く。既存 `barcodeSchema` の上限300等を流用）。
- **チェックディジット検証**: 数字13桁は `isValidEan13`、14桁は `isValidGtin14`（既存 `src/lib/barcode/ean13.ts`）で桁化け・読み落としを検出。
- **GS1構造チェック**: `analyzeBarcodeInput`（既存 `gs1.ts`）でAI構造・ロット/期限の妥当性を確認。壊れたGS1は採用しない。
- 検証NG → **「読み取り不良。もう一度読んでください」を即表示し、行は積まない**（不正値を通常行にしない）。専用の警告キュー（音・色）で気づかせる。

**E-2. 不明・複数候補（正しい形式だが商品に当たらない/絞れない）**
- 0件解決 → **「未登録／不明」行**として積む（黙って捨てない＝見落とし防止）。確定対象外。必要なら既存の未対応スキャン基盤（`BarcodeScanLog` / `/barcode/scans/unresolved`）へ後処理用に記録する設計余地あり。
- 複数解決 → **「複数候補」行**として警告。自動確定しない（現場制約・呼称Dの「候補展開して選ぶ」と接続）。

**E-3. 二重読み取り（スキャナのダブルトリガ）**
- 同一バーコードが**極短時間（例 200ms 以内）に連続**したら、スキャナの二重発火とみなして**2回目を無視**する（デバウンス）。
- 注意（トレードオフ）: 「同じ商品を2個続けて読む」正規操作は人間の速度（数百ms以上）なので加算される。デバウンスは“速すぎる重複”だけを吸収する。閾値は設定可能にし、取りこぼしは E-0 の一覧編集で救済。

**E-4. 連続して同じ誤りを読む（誤った商品/数量への加算）**
- **直近の読み取りパネル**を大きく常時表示（商品名・今回数量・確定後在庫・状態）。誤った商品が混ざった瞬間に気づける。商品写真があれば併記（`buildProductPhotoUrl` 流用）。
- **「直前の読み取りを取り消す」ワンタップ**を用意（行を探さず即修正）。
- **数量の急増ガード**: 1行の数量が閾値を超えたら注意色＋確認（同一商品への誤連打の検出）。組織設定の異常出庫しきい値（`organization-settings`）の考え方を流用可。

**E-5. フォーカス外れ・取りこぼし**
- スキャン欄を**常時オートフォーカス**し、確定・行操作・タップ/検索後もフォーカスを戻す。
- **「読み取り待機中／フォーカス外れ」状態を視覚表示**（外れていると気づける）。読み取り音・バイブ等の即時フィードバックで成功/警告/無視を区別する。

**E-6. スタッフバーコードとの取り違え**
- スタッフ／商品バーコードの自動判定（現場制約A）で、スタッフバーコードを商品として誤って積まない。判定に迷う値は「不明」行として扱い、自動確定しない。

これらは MVP でも E-0（安全網）＋E-1（検証）＋E-2（不明/複数）＋E-5（フォーカス）を最低限入れる。E-3・E-4 のデバウンス／急増ガード／取り消しは出庫モード実装と同時に入れると効果が高い。

#### F. 紙の納品書（将来: OCR照合。MVP外・別フェーズ）

- 現状、納品書は**紙**で届く。無バーコード商品もあるため、スキャンだけでは納品確認に穴が出やすい（オーナーの懸念）。
- アイデア: 紙納品書を**一括読み込み（撮影→OCR）**し、抽出明細をバーコード／発注（納品待ち `OrderRequest`）と突き合わせて受領を確認する。
- **無バーコードとの相乗効果**: 納品書ベースのチェックリストなら、バーコードが無い品も「チェックして受領」できる。スキャンの穴を紙の読み取りで埋められる。
- ハードル評価（段階）:
  - **低（現行設計）**: バーコードで1点ずつ納品スキャン。紙は人の参照用。無バーコード品はスキャン不可。
  - **中（現実的なおすすめ）**: 撮影→OCRで明細抽出→**既存「購入履歴インポート」のプレビュー&確認UX（既存一致／登録予定／確認必要／エラーに分類→人が確認して確定）を流用**。照合UIをほぼ再利用できるのが効く。課題は仕入先ごとのレイアウト差とOCR誤読（特に数量・コード）。**必ず人手確認を挟み、自動確定はしない。**
  - **最も確実**: 仕入先が**電子データ（CSV/Excel）**を出せるなら、既存インポートで高精度。OCRより楽。一部仕入先だけでも電子化できれば全体が軽くなる。→ 要確認事項（仕入先が電子明細を出せるか）。
- 位置づけ: spec.md の未実装「納品書照合／納品書画像保存」に該当。**MVP外・フェーズ5・別ハンドオフ**。MVP（フェーズ1）の納品はスキャン＋受領確認リストで回し、無バーコード品はリスト明細として照合する。
- 安全・プライバシー: 納品書に患者情報は載らない前提だが、画像・抽出データの保存範囲は最小化する。OCR外部サービスを使う場合も、秘密情報・APIキー実値はコードやドキュメントに書かない（環境変数）。

## 2. 画面の置き場所: 新設 `/barcode/batch` 案 vs 既存 `/barcode/stock` 拡張案

| 観点 | 新設 `/barcode/batch`（推奨） | 既存 `/barcode/stock` 拡張 |
| --- | --- | --- |
| 既存の1件ずつ確定フローへの影響 | なし。既存画面はそのまま残せる | 大きい。1件モードと一括モードのstate分岐が増える |
| 操作ミスのリスク | 低い。一括確定は専用画面に隔離される | 高い。1件即時確定と一括確定が同居し誤確定しやすい |
| UI実装の見通し | 良い。リスト保持・一括確定に特化できる | 悪い。既存フォームの責務が膨らむ |
| 学習コスト | 「一括は専用画面」と説明しやすい | モード切替の説明が複雑になる |
| 既存テストへの影響 | 既存テストは無改修で維持できる | 既存フォーム／アクションのテスト改修が必要 |

**結論: 新設 `/barcode/batch` を推奨。** 既存 `/barcode/stock`（1件ずつ即時確定）は安全な定番として残す。
`/barcode` 検索トップと `/barcode/stock` から `/barcode/batch` への導線リンクを足す。

将来 `/barcode/stock` 側に「この画面で読んだものを一括モードへ送る」導線を足すことは可能だが、MVPでは行わない。

## 3. MVP範囲（2026-06-09 優先度を再設定：納品が本丸）

優先度を入れ替え、**納品（スキャン＋受領確認リスト＋一括受領確定）を最優先**にする。出庫は軽量に保つ。

- **フェーズ1（最優先）: 連続納品モード＝スキャン納品＋受領確認リスト＋一括受領確定。** 「納品待ち1件だけ自動一致」を起点に、リストにためて一括で受領確定。無バーコード品はリスト行として扱える。
- **フェーズ2（軽量）: 連続出庫モード＝バーコード連続スキャン出庫のみ。** タップ／検索は作らない。
- フェーズ3: 納品の電子データ取込（ディーラーCSV/Excel）を同じ受領確認リストに追加（既存「購入履歴インポート」UX流用）。MVP外・後続。
- フェーズ4: 納品の確認必要処理（複数納品待ち候補の選択・発注先絞り込み・超過警告・ロット入力補助）。MVP外。
- フェーズ5: 紙の納品書OCRを同じ受領確認リストに追加（現場制約F）。MVP外・別ハンドオフ。
- フェーズ6: その他の高速化（発注先単位納品・GS1ロット期限反映・一括履歴の束ね表示）。MVP外。

> MVPは**フェーズ1＋フェーズ2**（どちらもスキャン主体・既存スキーマ変更なし）。納品を先に立ち上げる。

### スキーマ変更の要否（結論）

- **フェーズ1（納品）／フェーズ2（出庫）／フェーズ4（納品の確認必要）は既存スキーマ変更なしで実装可能。**
  - 納品は既存 `OrderRequest`（`receivedAt` 等）と `StockMovement.sourceType = "ORDER_RECEIPT"` をそのまま使う。
  - 出庫は既存 `StockMovement` / `StockItem` / `StockLot` をそのまま使う。
  - `StockMovement.sourceType` は文字列カラムなので、必要なら新しい値（例 `"BATCH_BARCODE_STOCK"`）を追加できるが、**MVPでは既存値を流用し、新値は足さない**（履歴表示・異常出庫検知などの下流影響を避けるため）。
  - フェーズ3（電子取込）も既存インポート基盤の流用で大きなスキーマ変更は不要見込み。フェーズ5（紙OCR）は別ハンドオフで判断。
- **「一括処理履歴の束ね表示」だけは要検討。**
  StockMovementに「同一バッチでまとめた」概念が無いため、束ね表示するには次のいずれかが必要。
  - 案1: 確定時に共通の `sourceId`（バッチID文字列）を全明細の `StockMovement` に入れて後からグルーピング（スキーマ変更なし、ただし `sourceId` の用途が混在する）。
  - 案2: 新規 `StockMovementBatch` テーブルを追加（スキーマ変更あり、きれいだが重い）。
  MVPでは束ね表示を作らないので、ここは未決のまま据え置く。

## 4. 共通の画面仕様（`/barcode/batch`）

サーバーコンポーネント `page.tsx` がログイン・アクティブクリニック・作業スタッフ候補を用意し、クライアントコンポーネントへ渡す。

ページ上部（共通ヘッダー領域）:

1. クリニック名表示（`context.clinicName`）。
2. **作業スタッフ選択**: **スタッフバーコード読み取りを主手段にする**（印刷済みスタッフバーコードを読む→続けて商品を読む）。読めない場合の代替として既存 `WorkStaffSelector`（ドロップダウン）も残す。`useWorkStaffSelection` の当日選択を localStorage 連携。未選択時は確定不可。**共有端末前提のため、スタッフ名は常時大きく表示し、各一括確定で明示確認＋ワンタップ切替（またはバーコード再読み取り）できるようにする**（名義事故防止。詳細は「1. 現場制約 A」）。
3. **モード切替**: 「**出庫モード**」「**納品モード**」のトグル。**画面を開いた既定は出庫モード**で、納品作業のときだけ納品モードへ切り替える。モードを切り替えたらためているリストは破棄確認する（混在防止）。

中央（スキャン入力＋リスト）:

4. バーコード入力欄（オートフォーカス。ハンディスキャナのEnter送出で1件追加）。入力値は `normalizeBarcodeText` で正規化。
5. ためているリスト（明細テーブル）。読み取った順に上から積む。
6. 各行で数量修正（±ボタンと直接入力）、行削除ができる。
7. 同じ商品を再度読んだら新規行を足さず既存行の数量を +1 する。

下部（確認と確定）:

8. 合計件数・合計数量のサマリ。
9. 警告がある行（在庫不足・未登録バーコード・納品待ちなし・複数候補など）を視認できる色分け。
10. 「内容を確認して一括確定」ボタン。確定前に確認リスト（または確認ダイアログ）を必ず表示。
11. 確定後は結果（成功件数・スキップ件数・各行結果）を表示し、リストを空にする。

### 読み取り時の通信（重要な安全ルール）

- **読み取り時点ではDBを一切変更しない。**
- 各スキャンで呼ぶのは**読み取り専用のサーバーアクション**（商品解決・在庫スナップショット・納品候補取得）のみ。`searchProductsByBarcode` 系の参照だけを使う。
- リストの保持はクライアントstate。確定時にリスト全体をサーバーへ送る。
- 確定アクションはクライアントが持つ情報を信用せず、**サーバー側で全件を再検証**してから1トランザクションで反映する。

## 5. 連続出庫モード仕様（フェーズ2 / 軽量・バーコードのみ）

### 操作フロー

1. 作業スタッフを選択。
2. モードを「出庫」にする。
3. 出庫理由を選ぶ（既定は `使用`。理由は既存 `barcodeStockOutReasons = ["使用", "その他"]` を流用）。MVPでは1バッチ＝1理由で運用し、行ごとの理由は持たない。
4. 商品バーコードを連続で読む。
5. 各スキャンで読み取り専用アクションを呼び、商品を解決してリスト行を作る／既存行を +1。
6. リスト行に表示する: 商品名、読み取りバーコード、数量、現在庫（スナップショット）、確定後在庫見込み（現在庫 − 数量）。
7. リスト上で数量修正・行削除ができる。
8. 在庫不足（確定後在庫が 0 未満）になる行は警告色にする。確定はできない、または該当行を除外してから確定する。
9. 「一括確定」で、商品ごとに在庫を減らし、行ごとに `StockMovement`（OUT）を残す。
10. すべて1トランザクションで安全に反映（全件成功か、全件失敗かを基本とする。除外を選んだ行は最初から対象外）。

### 出庫モードの入力口（バーコードのみ・2026-06-09 再設定）

- 出庫は**バーコードの連続スキャンのみ**。`searchProductsByBarcode` で1件解決→リスト追加／+1。
- **タップカード・名前検索は作らない**（当初の「出庫ステーション」構想は取り下げ。出庫は軽量なため）。
- 無バーコードの稀な出庫は、既存のクイック出庫（`/quick`）または在庫一覧の手動編集でカバーする。`/quick` は残す。

### スキャン時の商品解決ルール（出庫）

- `searchProductsByBarcode(clinicId, normalizedBarcode)` を使う。
- 0件 → 「未登録バーコード」行として警告。確定対象外。
- 2件以上 → 「複数候補」行として警告。MVPでは自動確定しない（確定対象外）。将来 `/barcode/stock` 同様の手動選択を足す余地あり。
- 1件 → 通常行として採用。`productId`・`stockItemId`・現在庫スナップショットを保持。

### GS1ロット・期限（出庫）

- 既存 `barcode-stock.ts` の `buildLotData` と同じ扱い。GS1でロット／期限が取れた場合、出庫時に該当ロットから減算する（`applyStockLotMove` 相当）。
- MVPではロット必須にしない。GS1でロットが取れない通常JANは商品単位の在庫数だけを減らす。
- 同一商品でも読み取りバーコードのロットが異なると在庫ロットの扱いが変わるため、**行のキーは「productId ＋ ロット情報」**にすることを推奨（同productでもロット違いは別行）。MVPで割り切るなら「ロット無しの通常出庫」を主対象にし、ロット付き行は数量加算せず1スキャン1行にする。

## 6. 連続納品モード仕様（フェーズ1・最優先 / MVP は単純一致から。受領確認リスト→一括確定）

「納品待ち」の定義（既存仕様）: `OrderRequest.status = "ORDERED"` かつ `receivedAt = null`。`getPendingOrdersByProduct` / `getPendingOrderDetailsByProduct` がこの条件で集計している。

### 操作フロー（MVP）

1. 作業スタッフを選択。
2. モードを「納品」にする。
3. 商品バーコードを連続で読む。
4. 読み取った商品に対し、同じクリニックの納品待ち `OrderRequest` を探す。
5. 納品待ちが**1件だけなら自動紐づけ**（その `orderRequestId` を行に保持）。
6. 複数ある場合は「確認必要」行として警告。確定前に選択が必要（**MVPでは確定対象外**。フェーズ4で選択UIを実装）。
7. 納品待ちが無い商品は「納品待ちなし」行として警告。確定対象外。
8. 発注数量（`requestedQuantity`）を超える読取数は警告。
9. MVPは「納品待ち1件に自動一致」ケースを優先実装する。
10. 一括確定時に該当 `OrderRequest` の `receivedAt` / `receivedQuantity` / `receivedMemo` / `receivedByUserId` / `receivedByStaffId` 等を更新。
11. 「在庫へ反映する」を選んだ場合は `StockMovement.sourceType = "ORDER_RECEIPT"`、`sourceId = orderRequest.id` で入庫履歴も残し、`StockItem` を増やす（必要ならロットも `StockLot` へ）。
12. ロット番号・有効期限はGS1で取れれば候補として持つが、MVPでは必須にしない。

### スキャン時の商品解決ルール（納品）

- 出庫と同様に `searchProductsByBarcode` で商品を1件に解決。0件＝未登録、2件以上＝複数商品候補で警告。
- 商品が解決できたら、その `productId` の納品待ち `OrderRequest` を取得（クリニック内・`status=ORDERED`・`receivedAt=null`）。
  - 0件 → 「納品待ちなし」警告（確定対象外）。
  - 1件 → 自動紐づけ。受領数量の既定は `requestedQuantity`（編集可）。
  - 2件以上 → 「確認必要」警告（MVPは確定対象外）。
- 既定の受領数量は発注数量。超過入力は警告し、確定時はサーバーで `requestedQuantity` 以下を強制（既存 `receiveOrderRequestForContext` と同じ制約）。

### 在庫反映の扱い（納品）

- 行ごとに「在庫へ反映する／しない」を選べる（既定は反映する）。既存の納品確認と同じ意味。
- 反映時の在庫行欠落（`StockItem` が無い）は既存同様エラーにする。MVPでは該当行を確定対象外にして他行は通す方針も検討（後述「エラー・警告ルール」）。

## 7. Server Action 設計

新規ファイル: `src/lib/actions/barcode-batch.ts`。
既存の `barcode-stock.ts` / `orders.ts` のロジックを再利用しつつ、**確定はリスト全体を1トランザクションで処理する専用関数**を作る。既存の単件関数はそれぞれ自前で `$transaction` と `revalidate` を行うため、ループ内でそのまま呼ぶのではなく、共通の下請けヘルパーを切り出して再利用する（重複ロジックの二重管理を避ける）。

### 7-1. 読み取り専用（スキャンごと、DB変更なし）

```
resolveBatchScanAction(input: { mode: "OUT" | "IN"; barcode: string })
  -> { kind: "ok" | "not_found" | "multiple_products" | "no_pending" | "multiple_pending";
       product?: { productId, productName, stockItemId, quantity, minStock };
       lot?: { lotNumber, expiryDateText, expiryDate } | null;   // GS1由来
       pendingOrders?: Array<{ orderRequestId, supplierId, supplierName, requestedQuantity, orderedAt }>; }
```

- 内部で `requireActiveClinic()` → `searchProductsByBarcode` → （納品時）`OrderRequest` 検索。
- 参照のみ。`revalidatePath` も `prisma` 書き込みもしない。

### 7-2. 連続出庫の一括確定

```
batchStockOutAction(prevState, formData)              // フォーム/サーバーアクション境界
batchStockOutForContext(context, input: {
  staffOperatorId: string;
  reason: string;                                     // 既定 "使用"
  reasonNote?: string;
  lines: Array<{ productId: string; quantity: number; barcode: string;
                 lot?: { lotNumber, expiryDateText, expiryDate } | null }>;
  skipShortageLines?: boolean;                         // true なら不足行を除外して確定
})
  -> { committed: Array<{ productId, productName, afterQuantity }>;
       skipped: Array<{ productId, reason }>; }
```

確定処理（1つの `prisma.$transaction` 内で全行ループ）:

1. 作業スタッフを `findActiveStaffOperatorByIdForClinic` で再検証。無効なら全体エラー。
2. 各行について `searchProductsByBarcode` で `productId` の整合を再確認（クライアント値を信用しない）。
3. `StockItem` を `clinicId + productId + isUsed=true + product.isActive` で取得。
4. OUTは `updateMany({ where: { id, quantity: { gte } }, data: { decrement } })` の楽観ロックで在庫不足を弾く（既存 `barcode-stock.ts` と同じ手法）。
5. 不足で `count === 0` の行は、`skipShortageLines` が true なら skipped に積んで継続、false なら**トランザクションを丸ごとロールバック**して全体エラー（確定不可）。
6. ロットがある行は `applyStockLotMove` 相当でロット在庫も減算。
7. 行ごとに `StockMovement`（OUT, `sourceType="BARCODE_STOCK"`, `performedByStaffId`, `memo="一括: 読み取りバーコード ..."`）を作成。
8. 全件成功で commit。最後に1回だけ `revalidatePath` 群を呼ぶ。

### 7-3. 連続納品の一括確定（単純一致 MVP）

```
batchOrderReceiveAction(prevState, formData)
batchOrderReceiveForContext(context, input: {
  staffOperatorId: string;
  lines: Array<{ orderRequestId: string; productId: string;
                 receivedQuantity: number; applyToStock: boolean;
                 receivedMemo?: string | null;
                 lot?: { lotNumber, expiryDateText, expiryDate } | null }>;
})
  -> { committed: Array<{ orderRequestId, productName, afterQuantity? }>;
       skipped: Array<{ orderRequestId, reason }>; }
```

確定処理（1つの `prisma.$transaction` 内で全行ループ。既存 `receiveOrderRequestForContext` の中身を下請けヘルパー化して再利用）:

1. 作業スタッフ再検証。
2. 各 `orderRequestId` に `lockTransactionKey(tx, "order-receipt:" + id)`（既存の advisory lock）。
3. `OrderRequest` を `clinicId` スコープで取得し、`status==="ORDERED"` かつ `receivedAt==null` を再確認。崩れていれば該当行を skipped（または全体エラー、後述の方針に従う）。
4. `receivedQuantity <= requestedQuantity` を強制。
5. `applyToStock` の行は `StockItem` 増加＋（ロットあれば）`StockLot` 増加＋ `StockMovement`（IN, `sourceType="ORDER_RECEIPT"`, `sourceId=orderRequest.id`, `performedByStaffId`）。
6. `OrderRequest` を受領済みへ更新（`receivedAt`/`receivedQuantity`/`receivedMemo`/`receivedLot*`/`receivedByUserId`/`receivedByStaffId`）。
7. commit 後に1回だけ `revalidateOrderPages` 相当を呼ぶ。

### リファクタリング方針

- 既存 `barcodeStockMoveForContext`（出庫）と `receiveOrderRequestForContext`（納品）から、**「1行ぶんのDB反映」部分を `tx` を受け取る純粋な下請け関数に切り出す**。
  - 例: `applyStockOutLine(tx, ctx, line)` / `applyOrderReceiptLine(tx, ctx, line)`。
- 単件アクションと一括アクションの両方が同じ下請けを呼ぶことで、ロジックの二重化を防ぐ。
- 既存単件関数の外部シグネチャは変えない（既存テスト・呼び出し元を壊さない）。

## 8. DB更新ルール

- 読み取り時: **書き込み禁止**。参照のみ。
- 確定時: **1リスト＝1トランザクション**。途中失敗は基本ロールバック（`skip*` オプションを選んだ警告行のみ事前除外）。
- 出庫の在庫減算は `updateMany + quantity gte` の楽観ロックで負在庫を防ぐ（既存方式踏襲）。
- 納品は `OrderRequest` 単位で `pg_advisory_xact_lock`（既存 `lockTransactionKey`）を取り、二重納品・競合を防ぐ。
- すべて `clinicId` / `organizationId` スコープで取得し、**別クリニック・別組織のデータを混ぜない**。
- `StockMovement` は行ごとに必ず残す（`beforeQuantity`/`afterQuantity`/`performedByStaffId`/`userId`/`memo`）。
- `sourceType` はMVPで既存値を流用（出庫 `"BARCODE_STOCK"`、納品 `"ORDER_RECEIPT"`）。新値は足さない。

## 9. エラー・警告ルール

スキャン時（行の警告。確定対象から外す）:

- 未登録バーコード（解決0件）。
- 複数商品候補（解決2件以上）。
- 納品モードで納品待ちなし。
- 納品モードで納品待ち複数（MVPは確定対象外＝確認必要、フェーズ4で選択）。

入力時（行の警告。修正を促す）:

- 出庫: 確定後在庫が 0 未満になる数量。
- 納品: `receivedQuantity` が `requestedQuantity` を超える数量。

確定時（サーバー再検証。MVPの既定方針）:

- 作業スタッフ未選択・無効 → **全体エラー**（1件も確定しない）。
- 出庫の在庫不足 → 既定は**全体エラー（確定不可）**。ユーザーが「不足行を除外して確定」を選んだ場合のみ該当行をスキップして継続。
- 納品で対象が `ORDERED`/`receivedAt=null` でなくなっていた（他者が先に処理）→ 該当行をスキップし、結果に「すでに納品済みのため除外」と表示（全体は通す）。競合は現場で起こりやすいため、ここは部分成功を許す方が実用的。
- 在庫反映時に `StockItem` が無い → 該当行スキップ＋警告表示（在庫一覧で在庫行を作るよう案内）。

自動確定しないもの（安全ルール）:

- 未登録バーコード、複数商品候補、納品待ち複数候補は自動で確定しない。
- 別クリニック・別組織データは対象にしない。
- 実在患者・実在クリニック名・秘密情報・環境変数実値は扱わない／書かない。

## 12. UI設計メモ

- 1画面に「ヘッダー（スタッフ・モード）」「スキャン入力」「ためているリスト（納品=受領確認リスト／出庫=出庫リスト）」「サマリ＋確定」を縦に積む。
- 出庫モード・納品モードとも入力は**バーコードスキャンのみ**（出庫のタップカード／名前検索は作らない）。
- ハンディスキャナ運用前提: スキャン欄は常時オートフォーカス。確定や行操作後もフォーカスをスキャン欄へ戻す。
- リスト行: 商品名 / 読み取りバーコード / 数量（±・直接編集）/ 現在庫 / 確定後見込み / 状態バッジ（OK・不足・未登録・複数候補・納品待ちなし・確認必要）/ 削除ボタン。
- 警告行は色分け（例: 不足＝赤、確認必要＝黄）。状態は既存の在庫ステータス表示（`getStockStatus`）と矛盾しない配色にする。
- 一括確定は誤操作防止に確認ダイアログ（**作業スタッフ名**・件数・合計数量・除外件数を表示）。共有端末前提のため、スタッフ名を目立たせ、違う場合はその場で切替できるようにする。
- 確定結果は「確定◯件 / 除外◯件」とその内訳をその場に表示。リストはクリアし、入力欄へフォーカス。
- ためているリストはクライアントstateのみ（リロードで消える）。MVPでは永続化しない。スキャン途中の離脱時に簡易な離脱警告を出す程度に留める。

## 14. 未決事項と決定（実装方針）

**全項目が決定済み（2026-06-09 オーナー判断）。Codexはこの通りに実装する。**


1. **出庫の在庫不足時** → **既定は全体ロールバック（1件でも不足があれば確定しない）。** あわせて画面に「不足行を除外して確定」ボタンを用意し、ユーザーが明示操作した時のみ不足行を除外して残りを確定する（`skipShortageLines=true`）。
2. **納品の競合（確定直前に他経路で受領済み）時** → **部分成功。** 競合した行だけ「すでに納品済みのため除外」として結果に表示し、残りの行は確定する。
3. **一括出庫の理由** → **1バッチ＝1理由。** バッチ開始時に理由（既定 `使用`）を1つ選び、全行に適用する。行ごとの理由はMVPでは持たない。
3a-0. **優先度（最重要）** → **納品が本丸。** 「スキャン納品＋受領確認リスト＋一括受領確定」を最優先（フェーズ1）。出庫は軽量でバーコード連続スキャンのみ（フェーズ2）。**出庫ステーション（タップ／名前検索）は取り下げ・作らない。** 電子取込・紙OCRは納品の後続フェーズ。（詳細は「1. 最優先方針」「3. MVP範囲」）
3b. **確定方式** → **すべてリストにためて一括確定。** 即時確定はしない。納品＝受領確認リスト、出庫＝出庫リスト、どちらもためて確定。
3c. **クイック出庫（`/quick`）の扱い** → **残す。** 出庫はバーコードのみとし、無バーコード出庫の受け皿として `/quick`（または在庫一覧の手動編集）を残す。
3d. **着地画面／トップ構成** → 設計裁量。**非破壊で二段構え**：まずホーム最上部に「納品」「出庫（バーコード）」への大きな導線を置き、運用が固まってからSTAFFのログイン後直接着地へ寄せる。ダッシュボードはADMIN向けに残す。
3d-2. **キオスク運用** → **共有端末は常時ログインのまま作業画面（納品／出庫）に据え置く。** ログインを朝1回に償却して最速化。名義は共通ログインではなくバッチごとのスタッフバーコードで担保。無操作で作業画面トップへ自動復帰、ADMIN機能は別ログインに分離。（詳細は「1. 導線とトップ構成／キオスク運用」）
3d-3. **操作モデル（再検証済み）** → **「画面で一括確定（ためて確認してから確定）」を維持。** スキャナのみ完結（コマンドバーコード）／即時確定＋取消も比較したが、誤読の安全網を優先して一括確定を採用。単品の即時1手化は将来余地。速度はキオスク化（ログイン償却）で取りに行く。（詳細は「1. 操作モデルの再検証結果」）
3e. **端末形態（複数スタッフ）** → **共有端末を交代で使う前提。** スタッフ名を常時大きく表示し、各一括確定でスタッフを明示確認＋ワンタップ切替。当日記憶は残すが共有端末の名義事故防止を優先。（詳細は「1. 現場制約 A」）
3e-2. **スタッフ識別方法** → **印刷済みスタッフバーコードの読み取りを主手段にする**（スタッフバーコード→商品バーコードの順）。ドロップダウン選択は代替。スキャン欄はスタッフ／商品バーコードを自動判定。1バッチ＝1スタッフ。（詳細は「1. 現場制約 A」）
3h. **クリニック呼称** → **段階2「呼称でまとめて探せる（在庫は製品別）」を採用。** 検索で同一呼称の複数SKUを表示しつつ、在庫・発注・期限はSKU単位で正確に保つ（プールしない）。クリニック単位のため小さなスキーマ追加。タイミングは実データ後・別ハンドオフ。（詳細は「1. 現場制約 D」）
3i. **出庫時の商品特定（無バーコード対応）** → **フォールバック順で扱う**: ①個にバーコード→読む ②包装のみバーコード（個別出庫）→**包装を読んで数量1** ③どこにも無い→タップ／名前検索 ④**内部バーコード／棚ラベルを発行して貼る（将来採用方針・オーナー関心あり）**。MVPは①〜③で回し、④は実データ（無バーコード割合）確認後に別フェーズで着手。`internalCode` はスキャン非対象なので、内部コードをスキャン可能にするには `ProductBarcode` 登録が必要。（詳細は「1. 現場制約 B」）
3j. **読み取り不良・連続誤読対策** → **多層防御**: ためて確定（安全網）＋読み取り検証（正規化・チェックディジット `isValidEan13`/`isValidGtin14`・GS1構造）＋不明/複数候補は確定対象外で可視化＋二重読み取りデバウンス＋直近読み取りパネル＋直前取り消し＋数量急増ガード＋フォーカス保持。MVPは安全網・検証・不明扱い・フォーカスを最低限入れる。（詳細は「1. 現場制約 E」）
3f. **入数（袋→個の換算）** → **段階導入。** MVPは案1（スキーマ変更なし・在庫は個で数える・数量は手入力）。案2（`ProductBarcode` に既定入出庫数量を追加して自動換算）は次フェーズ・別ハンドオフ。（詳細は「1. 現場制約 C」）
3g. **在庫の数え方** → **最小単位（個）で数える。** 納品は個換算した受領数を入れる。1個バーコードなし出庫は包装読んで数量1、無ければ既存クイック出庫／手動。
4. **ロット付き出庫の行集約ルール** → ロットなしの通常出庫を主対象に数量+1。ロット付き（GS1由来）は1スキャン1行で分け、数量加算しない。
5. **`StockMovement.sourceType` の扱い** → 一括専用の新値は足さず既存値を流用（出庫 `BARCODE_STOCK` / 納品 `ORDER_RECEIPT`）。将来の束ね表示を作る段階で再検討。
6. **「一括履歴の束ね表示」** → MVPでは作らない。将来やる場合は「共通sourceId流用」か「新テーブル」かを別途判断。
7. **ためているリストの永続化（リロード耐性）** → MVPでは持たない（リロードで消える）。離脱時に簡易警告のみ。
8. **モードの名称と既定** → モードは「**出庫モード**」「**納品モード**」の2つ。**画面を開いた既定は出庫モード**とし、納品作業のときだけユーザーが納品モードへ切り替える。ナビ／画面見出しもこの2語で統一する。

## 15. 実データ到着時の確認チェックリスト

実製品データ（商品マスタ）を受領予定。**MVP（案1・スキーマ変更なし）はデータを待たずに着手できる**（数量を常に手入力・編集可にしてあり、データ形状に依存しないため）。一方、**案2（入数の自動換算・スキーマ変更）とUXチューニングはデータを見てから設計する**。データが届いたら以下をプロファイリングし、その結果を本書（特に「現場制約 C」）と案2ハンドオフに反映する。

### 15-1. 入数・包装（案2の設計判断に直結）

- 何個入りの包装が多いか（入数の分布: 1/3/5/10 など）。1袋あたりの個数の代表値。
- バーコードは「包装（袋・箱）」に付くのか「バラ1個」に付くのか、その割合。
- 同一商品で「包装バーコード」と「バラバーコード」が両方あるか（→ 既定数量を `ProductBarcode` 単位で持つ必要性の判断）。
- 入数は「商品ごとに1つ」で足りるか、「バーコード（包装種別）ごと」に必要か。
- → これらで案2のスキーマ形（`Product` に入数 vs `ProductBarcode` に既定数量）と既定値を決める。

### 15-1b. クリニック呼称・グルーピング（現場制約 D の設計判断）

- 「同じ呼称で扱う別SKU」（例: グローブ＝製品A・B）が実際にどれだけあるか。代表的なグループと規模。
- 呼称はクリニックごとに違うか（院ごとに呼び方が分かれるか）。→ 呼称をクリニック単位で持つ必要性の確認。
- 「製品ごとの別名」で足りるか、「呼称グループ（多対一）」が必要か。→ 呼称のスキーマ形（`StockItem` の呼称カラム vs `ClinicProductAlias` / 呼称グループ・テーブル）を決める。

### 15-2. バーコード保有状況（無バーコード対応・検索の重要度）

- 全商品のうちバーコード（`janCode` または `ProductBarcode`）を持つ割合。無バーコード商品の実数。
- バーコードの種別（JAN13 / GS1 / その他）と桁の整合。
- 重複・表記揺れ（全角/半角、ハイフン）。`normalizeBarcodeText` で吸収できる範囲か。
- 1バーコードが複数商品に解決してしまう（重複登録）ケースの有無。→ 「複数候補」警告の発生頻度見積り。

### 15-3. 在庫の単位（「個で数える」前提の検証）

- 現状の在庫数が「個」で記録されているか、「袋・箱」混在になっていないか。
- 混在があれば、移行時に個へ寄せる方針・対象を別途検討（本MVPの前提「個で数える」と突き合わせ）。

### 15-4. カテゴリ・件数（UXチューニング）

- 商品総数（検索・カードの表示性能の目安）。
- カテゴリ構成と件数分布（タップカードのタブ設計、よく使う商品の絞り込み）。
- 商品名・カナの充足度（名前検索のヒット品質）。

### 15-5. 進め方

- データ受領後、上記を一度集計（プロファイリング）し、要約を `docs/dev-log.md` に残す。
- 案1（MVP）の前提に反する点がないか確認（特に 15-3）。
- 案2の設計は、15-1・15-2 の結果を根拠に別ハンドオフで具体化する。
